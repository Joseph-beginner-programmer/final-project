## Key Architectural Decisions Made

1. **No real-time UI (WebSockets/Reverb)** — decided against it after analysis. `BROADCAST_CONNECTION=log` (no-op) for now, code stays broadcast-ready for later.
2. **Real-time backend cache IS required** — `products.current_stock` must update synchronously, in the same DB transaction as any `stock_movements` write, using `lockForUpdate()` to prevent race conditions/lost updates under concurrency. This replaces the need for live UI push for the inventory-concurrency risk.
3. **Concurrency protection = transactions + row locking**, not WebSockets. This is the actual defense for the "two staff allocate same stock" risk.
4. **Enum values stored as English/underscore** in DB (e.g. `finished_goods`, not `barang jadi`) — Bahasa Indonesia labels handled via a `label()` method on PHP backed enums, kept as a display-only concern.
5. **Architecture layers**: Controllers/Livewire = thin, orchestrate only. `Services/` = workflows (multi-step). `Actions/` = single atomic operations. `Events/`+`Listeners/` = decoupled side effects. `Enums/` = replace magic strings. `Observers/` = model lifecycle side effects (e.g. audit log). `Policies/` = model-tied authorization. `Gates/` = non-model authorization (e.g. dashboard access). `DTOs/` = only once a workflow has 5+ related fields, not for simple forms.
6. **Validation layering established:**
   - **Input validation** (Form Requests): is a single field well-formed (numeric, required, etc.)
   - **Business validation** (inside Actions): is the object, in its current state, allowed to do this (e.g. status checks)
   - **Authorization** (Policies/Gates): is *this user* allowed to do this at all, regardless of object state
7. **Derived/cached fields must never be set directly** — `products.current_stock`, `purchase_order_items.subtotal`, `purchase_orders.total_amount`, `purchase_order_items.quantity_received` are all calculated from their source data (movements/receipts), not entered independently.
8. **Never edit vendor files.** Fortify customization done via container binding (see below), not editing `vendor/laravel/fortify/...`.

## Purchasing Domain Models — Implemented (Eloquent)

All 6 models exist under `app/Models/` with real business logic already written (this was built before it got documented here — handover previously understated actual progress):

- **`Supplier`** — `#[Guarded(['id'])]`. `purchaseOrders(): HasMany`, `products(): BelongsToMany` (via pivot, see below).
- **`Product`** — `#[Guarded(['id', 'current_stock'])]`. Casts `type` to `ProductType` enum + 3 decimal fields. `scopePurchasable()` local scope (`where type = raw_material`). `isBelowReorderPoint()` uses `bccomp()` — **all quantity/money comparisons in this codebase use bcmath (`bccomp`/`bcsub`/`bcmul`), never raw float comparison**, to avoid binary floating-point rounding error compounding across a ledger.
- **`ProductSupplier`** — custom `Pivot` subclass (`#[Table('product_supplier')]`, `extends Pivot` not `Model`), casts `price` to `decimal:2`. Wired via `->using(ProductSupplier::class)` on both `Product::suppliers()` and `Supplier::products()`, since the pivot carries real data (price), not just a join.
- **`PurchaseOrder`** — `#[Guarded(['id', 'po_number', 'status', 'approved_by', 'approved_at', 'total_amount'])]` — every system-derived field locked out of mass assignment. Relations: `supplier()`, `createdBy()`/`approvedBy()` (both `BelongsTo(User::class)` on different FKs), `items(): HasMany`. **Status is a finite state machine**: `transitionTo(PurchaseOrderStatus $target)` is documented as "the ONLY method allowed to change this PO's status" — it calls `$this->status->canTransitionTo($target)` (lives on the enum) and throws `InvalidStatusTransitionException` if illegal. `recalculateTotal()` re-sums `items()->sum('subtotal')` — total is never hand-set.
- **`PurchaseOrderItem`** — `#[Guarded(['id', 'quantity_received', 'subtotal'])]`. `syncSubtotal()` computes via `bcmul()` but deliberately does **not** call `save()` — caller controls when it's persisted (e.g. inside a larger transaction). `remainingQuantity()` and `isFullyReceived()` also bcmath-based.
- **`PurchaseOrderReceipt`** — `#[Guarded(['id'])]`. One row per delivery event against one PO item; `purchaseOrderItem()`, `receivedBy()` (→ `User`).

**`PurchaseOrderStatus` enum** (`app/Enums/PurchaseOrderStatus.php`) — 8 cases: `Draft`, `PendingApproval`, `Approved`, `Rejected`, `PartiallyReceived`, `FullyReceived`, `Cancelled`, `Closed`. Transition graph lives in `canTransitionTo()`.

The state machine now matches the originally documented design. `RejectPurchaseOrderAction` itself is still not written (see Actions table).

**✅ RESOLVED (between Sessions 15 and 16, confirmed 2026-10-05):** `Closed` is now a live enum case (`PartiallyReceived → Closed`, `FullyReceived → Closed`), `ClosePurchaseOrderAction` exists (sets `closed_by`/`closed_at`/`close_reason` alongside `transitionTo(Closed)`), migration `2026_10_05_000000_add_close_fields_to_purchase_orders_table.php` has run, and a Close button + reason modal is wired into View PO. Not yet added to `lang/id.json` (still English-only fallback). Went through a few review rounds too — `$requested`/`$available` were briefly typed `int` (would've truncated fractional quantities) before being fixed to `string`, and `userMessage()` briefly referenced bare `$requested`/`$available` instead of `$this->requested`/`$this->available` (undefined-variable bug — promoted constructor params aren't visible as local variables in a different method) before being corrected.

**Relations wired into existing models to support the ledger:**
- `Product::stockMovements(): HasMany` (`app/Models/Product.php`) — **renamed from the initial `stockMovement()`** (singular-name inconsistency flagged during review, since fixed) for consistency with `purchaseOrderItems()` etc.
- `PurchaseOrderReceipt::stockMovements(): MorphMany` (`app/Models/PurchaseOrderReceipt.php`) — the inverse side of `StockMovement::reference()`; correctly plural. This is the first real polymorphic relation in the codebase.

**Morph map registered** in `AppServiceProvider::boot()`: `Relation::morphMap(['purchase_order_receipt' => PurchaseOrderReceipt::class])`. Deliberate choice over Laravel's default (storing the fully-qualified class name in `reference_type`) — decouples the DB column from the PHP namespace, so a future `App\Models\...` rename/refactor doesn't silently orphan existing ledger rows. Only one entry exists so far; every future `reference_type` source (sales shipments, production consumption, etc.) will need its own map entry added here as those modules get built.

**✅ DECIDED (Session 7): over-receipt / negative-stock policy.** Two related but distinct policy questions, both resolved this session:
- **Negative stock (in `CreateStockMovementAction`):** blocked. An `Out` movement that would push `current_stock` below zero throws `InsufficientStockException` before any write happens (checked via `bccomp($newStock, '0', 2) < 0`, scoped to `Direction::Out` only — an `In` movement can mathematically never go negative).
- **Over-receipt (for the still-unwritten `ReceivePurchaseOrderAction`):** **allowed freely** — a receipt can push `purchase_order_items.quantity_received` past `quantity_ordered`. Chosen over blocking/capping because the project's own priority (architectural decision #2) is that `products.current_stock` stay accurate to physical reality; capping or blocking a receipt that reflects what was *actually* physically delivered would desync the system from the warehouse floor, which is worse than a "messy" paper trail. `PurchaseOrderItem::isFullyReceived()` already uses `bccomp(...) >= 0` (not `== 0`), so it's already compatible with this decision with no code change needed; `remainingQuantity()` will need a floor-at-0 clamp wherever it's displayed, since it can now go negative.

**`ReceivePurchaseOrderAction` step sequence — ✅ finalized (Session 7, 2026-08-03), revised from the original plan below, not yet coded:**

Operates on **one `PurchaseOrderItem` per call** (matches `purchase_order_receipts.purchase_order_item_id`'s per-item FK and the existing granular-Action convention — a shipment covering multiple items means multiple calls). All inside one `DB::transaction()`:
1. Lock the `PurchaseOrderItem` row (`lockForUpdate()`) — same concurrency reasoning as the `Product` lock inside `CreateStockMovementAction`, applied one level up (two staff recording receipts against the same line item at once).
2. Business validation — explicit status guard (`Approved`/`PartiallyReceived`), likely a small `PurchaseOrder::ensureCanReceive()` model helper mirroring `ensureIsEditable()`'s shape. **This check is necessary here even though `PurchaseOrderPolicy::receive()` already checks the same condition** — unlike `ApprovePurchaseOrderAction`/`RejectPurchaseOrderAction`, this Action doesn't unconditionally call `transitionTo()` (see step 6), so there's no guarantee anything else in the call path validates status on every invocation.
3. ~~Quantity check / block over-receipt~~ — **not needed.** Over-receipt is allowed by design decision (see "Inventory Domain Models" above) — no cap, no block.
4. Create the `purchase_order_receipts` record. `received_at` is **not** caller-suppliable (dropped from `ReceivePurchaseOrderData` deliberately) — set to `now()` inside the Action, same reasoning as `createdBy` not being caller-suppliable on `CreatePurchaseOrderAction`.
5. Recompute `purchase_order_items.quantity_received` as a fresh `SUM()` over that item's `receipts()` (not an increment) — mirrors `PurchaseOrder::recalculateTotal()`'s pattern, self-heals if a receipt is ever corrected/voided later. Suggested new model method: `PurchaseOrderItem::syncQuantityReceived()`, same "computes, doesn't `save()` itself" shape as `syncSubtotal()`.
6. Recalculate PO overall status by checking **every** item via `isFullyReceived()` (already `>=`-based, no change needed): all fully received → target `FullyReceived`; some but not all → target `PartiallyReceived`. **Only call `$po->transitionTo($target)` if `$target !== $po->status`** — `PurchaseOrderStatus::canTransitionTo()` does not allow `PartiallyReceived → PartiallyReceived`, so a second still-partial receipt against an already-`PartiallyReceived` PO must skip the `transitionTo()` call entirely or it throws `InvalidStatusTransitionException` incorrectly.
7. Call `CreateStockMovementAction::handle()` — `direction: In`, `type: PurchaseReceived`, `amount` = this receipt's quantity, `referenceId`/`referenceType` = the just-created `PurchaseOrderReceipt`'s id + the `'purchase_order_receipt'` morph-map key. Safe to call from inside this Action's own outer transaction — Laravel nests `DB::transaction()` calls via savepoints automatically.
8. Fire `PurchaseOrderReceived` event → no listener needs to exist yet (decoupled side-effect seam, same reasoning as architectural decision #1 — not a half-finished feature, just an extension point).

## Purchasing Actions Implemented (Session 3, 2026-07-14/15)

**`app/Actions/Purchasing/CreatePurchaseOrderAction.php`** — takes `App\DTO\Purchasing\CreatePurchaseOrderData` (note: folder is `DTO`, singular — renamed from an initial `DTOs`). Crosses the project's own "5+ related fields → use a DTO" threshold (supplierId, orderDate, expectedDeliveryDate, createdBy, items[]). Steps, all inside one `DB::transaction()`:

3. Items are **optional at creation** (`$data->items = []` default) — matches the existing rule that "≥1 item, qty > 0" is enforced later at `SubmitPurchaseOrderForApprovalAction`, not at Create. Supports both "fill the whole form at once" and "start blank, add items later" flows.

- Authorization is deliberately **not** inside the Action — assumes the caller already checked `Gate::authorize('create', PurchaseOrder::class)`. ### 2. `app/Http/Responses/LoginResponse.php`
Custom Fortify `LoginResponse` implementation — redirects by role instead of Fortify's generic default.

<?php

namespace App\Http\Responses;

use Illuminate\Http\RedirectResponse;
use Illuminate\Support\Facades\Auth;
use Laravel\Fortify\Contracts\LoginResponse as LoginResponseContract;

class LoginResponse implements LoginResponseContract
{
    public function toResponse($request): RedirectResponse
    {
        $user = Auth::user();

        return redirect()->intended(
            route($user->role->dashboardRoute(), absolute: false)

    }

<?php

namespace App\Providers;

use App\Enums\UserRole;
use App\Http\Responses\LoginResponse;

use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider

**Session 3 (2026-07-14/15):**
6. **Guarded fields were being silently dropped via mass assignment from inside the model's own methods** — `PurchaseOrder::transitionTo()` and `recalculateTotal()` originally did `$this->update(['status' => $target])` / `update(['total_amount' => ...])`, but `status` and `total_amount` are both in `#[Guarded([...])]`. Fixed with one line: `parameters.parseModelCastsMethod: true`.
8. **Project root had 5 empty/junk files** (`'Test`, `'purchasing'`, `'purchasing@test.com'`, `bcrypt('password')`, `npm`) — accidental artifacts from a shell-quoting mishap (Windows/PowerShell doesn't treat single quotes the way bash does), unrelated to the app. Deleted. ### Three real bugs found and fixed this session (not UI polish — genuine full-stack debugging)

1. **Theme reverting to dark on every reload.** Root cause: **two independent Alpine.js instances on one page.** `resources/js/app.js` had `import Alpine from 'alpinejs'; window.Alpine = Alpine; Alpine.start()` — but Livewire *already* bundles and auto-starts its own Alpine (via `@fluxScripts`), and Flux's appearance-store logic (traced through the vendor JS bundle, `vendor/livewire/flux/dist/flux.min.js`) is written assuming exactly one instance exists. Two instances racing to initialize on each load explained the inconsistent, order-dependent behavior (same-origin confirmed, no thrown errors, since these are genuinely separate module instances that don't share Alpine's own duplicate-`.start()` warning flag). Fixed by stripping `app.js` back to empty — nothing in the codebase depended on the manually-imported `@alpinejs/mask` plugin at the time.
2. **`x-mask` money formatting, three separate bugs in sequence** as the user built a Rupiah input mask: (a) plugin never registered — `app.js` referenced `mask` in an `alpine:init` listener with no `import mask from '@alpinejs/mask'`, threw `ReferenceError` and silently no-opped the whole directive; (b) `$money($input, ',', '.' 0)` — missing comma made it invalid JS, threw `SyntaxError`; (c) even once syntactically valid, `$money()`'s actual signature (verified by reading `node_modules/@alpinejs/mask/src/index.js`) is `(input, delimiter, thousands, precision)` where `delimiter` is the *decimal* character, not thousands — the user's original argument order/count put values in the wrong slots.
3. **Unit price showing `3.000.000` for a `30000.00` value (100× inflated).** Root cause: `formatMoney()` with `precision: 0` strips any character that isn't a digit or the configured decimal-delimiter — since the bound value came straight from a `decimal:2`-cast Eloquent attribute (always has a literal `.00`), and `.` wasn't configured as the decimal delimiter, the `.00`'s two digits got silently absorbed as extra whole-number digits, inflating the display by 100×. Fixed at the source, not in the mask config: `(string) (int) $item->unit_price` in `syncItemsFromModel()`, so a decimal point never reaches the masked input at all — consistent with the project's standing "Rupiah has no cents in practice" stance from Session 5.

Also: caught the user leaving a debugging `dd()` inside the `updated()` hook after using it to confirm a computed value — explained that `dd()` doesn't just dump, it **terminates the script**, so the Livewire request never completes/re-renders while it's still there; looked like "the value won't populate" but was actually "the response never arrives."

### Costing method decided: FIFO (for the future Work Order/Production module)
User confirmed the Cost Accounting module (see "Future module note" above) will need to extract **material cost** per production run once Work Orders exist — asked whether the current PO/stock setup supports that. Verified against the actual migrations (not from memory) before answering: `purchase_order_items.unit_price` is real acquisition-cost data, but `stock_movements.amount` is a plain `decimal(12,2)` **quantity**, no cost/currency semantics at all. Once stock is received, it pools into one `products.current_stock` number — there's no batch/lot memory of which PO a given unit of stock came from, so a future Work Order's `stock_movements` "out" row (material consumed) currently has no way to answer "at what cost."

**Two costing approaches were discussed; user chose FIFO over the simpler Weighted Average Cost (WAC) option:**
- **WAC** would have been a single cached `products.average_cost` column, recalculated on every `in` movement (weighted by quantity) — cheap, fits the existing "cached/derived field, recalculated under `lockForUpdate()`" pattern used for `current_stock`/`total_amount` elsewhere. Rejected in favor of accuracy.
- **FIFO** (chosen) requires real batch/lot tracking since consumption must draw from the oldest batch first, potentially splitting a single consumption event across multiple differently-priced batches. This needs **two new tables**, not built yet:
  - **`stock_lots`** — one row per batch that ever entered inventory: `product_id`, a link back to the `stock_movements` row that created it, `unit_cost`, `quantity_received` (immutable), `quantity_remaining` (mutable, decremented as FIFO draws from it), `received_at` (defines draw order). Conceptually this is a *mutable balance* table (same category as `products.current_stock`), not an *immutable ledger* like `stock_movements` — a genuinely new "kind" of table for this codebase, though consistent with the existing cached-balance pattern.
  - **An allocation table** (e.g. `stock_movement_lot_allocations`) — records exactly which lot(s) a given `out` movement drew from and how much, since one movement can span multiple lots at different costs. Without this, a `stock_movements` row alone can't answer its own cost once it spans more than one lot.
- **Sequencing decision:** lot *creation* (the `in` side) should be added to `CreateStockMovementAction`'s existing `in` path once this is picked back up — cheap relative to rebuilding it later. Lot *consumption/draw-down* (the FIFO walk, `out` side) should wait until the Production/Work Order module actually exists to call it, consistent with the project's standing "don't scaffold untestable pieces" rule (same reasoning already applied to the low-stock notification in Session 6).
- **⚠️ Correction/risk flagged after re-reading this file, not caught during the live discussion:** `CreateStockMovementAction` and `ReceivePurchaseOrderAction` are **already written and in use** (Sessions 7–8), including real dev/test data (the `warehouse@test.com` manual-testing account). This means real `stock_movements` "in" rows almost certainly already exist **without** a corresponding lot. Adding lot-creation to the Action now does not retroactively backfill those — when FIFO consumption logic is eventually built, any stock that predates the lot-tracking change will need to be treated as one lump "opening balance" lot (a normal ERP-migration pattern, not a blocker, but a real decision to make explicitly rather than discover as a bug).
- **Explicitly deferred, not solved:** what "cost" means for a `ProductionOutput` movement (finished goods entering inventory) — not a purchase price, but a rollup of that Work Order's own material+labor+overhead cost. Fully blocked on the Work Order feature itself existing. Also deferred: whether `stock_movements` gets its own cached `total_cost` (summed from that movement's lot allocations) for reporting convenience — likely yes, same "cache the derived total" precedent as `subtotal`/`total_amount`, but only worth adding once the allocation table exists.

### Costing table renamed and scoped down (Option A, deliberately) — `raw_material_lots`
Picked up the FIFO discussion from Session 11 and pushed it further: confirmed (by reading the actual `ReceivePurchaseOrderAction` code, not assumed) that one `PurchaseOrderReceipt` produces exactly one `StockMovement` today, even though the relation is a `MorphMany` (schema allows more, current code just never creates more than one). ### Production module — architecture brainstorm (guide-only, nothing built; user explicitly building the schema themselves next)

Long back-and-forth, user leading with their own ideas each time and only asking the assistant for pushback/opinion at specific points (the standing "don't volunteer a recommendation unless asked" rule held throughout — assistant asked clarifying questions and reflected tradeoffs back rather than proposing solutions, until the user explicitly asked "what do you think" at two points). Nothing has been migrated, modeled, or coded — this is 100% design discussion to pick up from next session.

**Decisions reached, in the order they were reasoned through:**

1. **No fixed-step "production formula" with baked-in costs.** Original idea was a reusable formula defining ordered steps (Mixing → Cutting → Packaging) each carrying its own cost. Abandoned once the user realized raw material cost is FIFO-derived (varies every time, depending on which lots get drawn) — a formula can't pre-bake a cost that isn't knowable until actual consumption. Landed instead on: **everything (machine, worker, material, and therefore cost) gets decided fresh at the Work Order/Production Plan stage**, not defined in advance by a template.

2. **BOM is needed, but scoped to just material quantities, and is completely non-enforced.** A BOM exists per producible product (both WIP and Finished Goods need one, not just top-level finished goods) — defines *what materials, how much*, nothing about cost or sequence. Explicitly decided to be **just a template/pre-fill helper with zero enforcement** — a Work Order is free to deviate from its product's BOM entirely (different materials, different quantities). This means no validation code is needed to check "does this Work Order's material list match its BOM" — that check simply doesn't exist by design, not an oversight.

3. **`ProductType::Wip` already exists in the enum** (`'wip'` case, alongside `RawMaterial`/`FinishedGoods`) — added early, unused until now. Confirmed by reading the file, not assumed.

4. **WIP is a real consumable input, not just an inventory state.** A Work Order can consume a WIP item as material input the same way it consumes raw materials — meaning multi-stage chains are real (Plan A: raw materials → WIP; Plan B: that WIP → finished goods), not just a status label.

5. **One `WorkOrder` model, not several.** A single Work Order is scoped to **exactly one hop** — either raw materials → WIP, or WIP → finished goods — never the full raw-to-finished-goods chain in one record. Which hop a given instance represents is just data on that instance (a `hop_type`-style field, or derivable from the input/output product types), not a separate model/table per hop type. This also resolved an earlier concern the assistant raised about dropping "steps" losing shop-floor process visibility — steps aren't gone, they're promoted to be first-class Work Orders themselves, one per real production stage.

6. **Work Order output tracked as a lot, in one shared table — `work_order_output_lots`.** Every completed Work Order's output (WIP or finished goods) becomes its own trackable, cost-bearing, FIFO-drawable unit, same shape as `raw_material_lots`. Decided explicitly **against** splitting WIP-lots and Finished-Goods-lots into two tables: they're structurally identical (same origin — one `work_order_id` FK, same fields), the only difference is what `Product::type` the linked product happens to be — and this codebase already has a standing precedent for not splitting tables over `Product::type` (`products` itself is one table for all three types). Splitting would also mean duplicating the FIFO-draw-down query across two tables for zero real behavioral gain; the "don't let a Sale draw from a WIP lot" protection is just as reliable as a `whereHas('product', ...)` query scope on one shared table. Name chosen to describe the *origin* (what created it — a Work Order), mirroring how `purchase_order_receipt_batches` is named after its origin, not its contents — not `work_in_progress_product_lot` (the user's first instinct), since that name stops fitting once the table also holds finished-goods lots.

7. **Production lot cost must be computed once at completion and *stored*, unlike `raw_material_lots`' derive-live design.** `raw_material_lots` gets away with deriving cost on the fly because it's one cheap relation hop (`lot → receipt → item → unit_price`) to a value that's frozen once the PO leaves Draft. A Work Order's output cost is a rollup of a *variable-length list* of consumed input lots (raw material and/or WIP, possibly several) plus labor plus machine cost — recomputing that later would mean replaying the entire consumption history. So `work_order_output_lots` needs its own stored cost column (a cached/derived field, guarded from mass-assignment, same treatment as `products.current_stock`), computed once when the Work Order completes. A Finished-Goods lot's cost is therefore a further rollup **of WIP lot(s) already-computed cost** (plus that hop's own labor/machine) — the cost chain cascades through however many hops a chain of Work Orders has, each link using the previous link's already-stored number.

8. **A new "allocation" table is needed to record which lot(s) a Work Order's consumption drew from and how much** — necessary because one consumption event can legitimately span multiple differently-costed lots (FIFO splitting across lot boundaries), same reasoning already sketched (but never built) for the raw-material case back in Session 9. This table needs a **polymorphic `lot_type`/`lot_id`** (`morphTo`), reusing the exact idiom already established for `stock_movements.reference_type`/`reference_id` (a morph-map string key, not a raw FQCN) — because it points at two genuinely separate, differently-shaped, independently-existing tables (`raw_material_lots` and `work_order_output_lots`), unlike the WIP/FG-lot question above where the two things being unified were structurally identical. Two new morph-map entries will be needed in `AppServiceProvider::boot()` alongside the existing `'purchase_order_receipt'` one.
   - **Sequencing dependency, flagged explicitly:** this allocation table can't actually be built first in isolation — it needs an FK to *which Work Order's consumption* a row belongs to, so at minimum a skeleton `work_orders` table has to exist before or alongside it.
   - **Open, deliberately deferred by the user** ("let me try it myself first"): whether an allocation row references the Work Order directly (giving only "total material cost for this Work Order," no breakdown), or a more granular per-material-line identity within the Work Order (so cost can be broken down *by which material*, not just totaled) — matters if the future Cost Accounting module needs a materials breakdown, not just a total. **Not decided — pick this back up once the user has shaped the `work_orders` table.**

9. **Precision/rounding risk flagged, not yet resolved:** raw material inputs are measured in fractional KG (e.g., 1.36 kg of plastic) — multiplying `unit_price × quantity_drawn` for an allocation's cost is safe (no division involved), but computing a *new* lot's cost (rollup ÷ quantity produced) is a genuine division that can produce a non-terminating decimal, and this project's existing `decimal(12,2)` convention (fine for Rupiah amounts) may not carry enough precision for a value that gets multiplied forward again at the next hop — rounding error compounding across a multi-hop chain is exactly the failure mode `bcmath` discipline exists to prevent elsewhere in this codebase. **Possible direction floated, not committed to:** never store a divided *per-unit* cost at all — store each lot's *total* cost only, and compute whatever fractional proportion is needed fresh via `bcdiv`/`bcmul` at the moment of use, so rounding only ever happens once, at final display, never mid-chain. **Confirmed by the user:** production *output* quantities (termos body, lid, etc.) are always whole units/integers — the fractional-precision risk lives entirely on the raw-material *input* side, not the output-quantity side. Practical implication: `work_order_output_lots`' quantity/remaining-stock field can likely just be a plain integer column, unlike `raw_material_lots.remaining_stock` (`decimal(12,2)`).

**Nothing from this list has been migrated, modeled, or coded yet.** Next session should resume once the user has drafted the `work_orders` table shape themselves.

## Concepts Already Taught (don't re-explain unless asked)
- **(Session 18) `stock_movements` ↔ `inventory_lots` and FIFO:** lots are the mutable per-batch balance, movements the immutable ledger (one OUT row per lot drawn). Three invariants: `current_stock` = Σ IN − Σ OUT = Σ lot `quantity_remaining`; per lot `quantity_remaining` = `quantity_initial` − Σ its OUT movements. The draw that empties a lot takes its whole `value_remaining` so rounding never strands rupiah.
- **(Session 18) How WIP gets its unit cost:** (material at FIFO + labor + overhead) ÷ good quantity; normal rejects are absorbed by good units, abnormal rejects go to `abnormal_loss_cost`; store total value, not only the unit cost.
- **(Session 18) Why `material_issue_item` is in the morph map:** `stock_movements.reference_type/reference_id` is polymorphic (one FK column pointing at different tables). The map stores a stable key instead of the PHP class name, and works in both directions: `morphMany` builds its `WHERE reference_type = …` from the map (a missing entry silently returns nothing, e.g. an empty FIFO trail), and `morphTo` resolves the key back to a class. Movements point at the *line*, not the document, because one movement = one product from one lot.
- **(Session 18) `quantity` vs `quantity_consumed` on `material_issue_items`:** `quantity` = what left the warehouse (set at posting); `quantity_consumed` = what production actually used (set by the production result). The difference is material on the floor, out of `current_stock` but not yet in any product. Both cost columns are system-computed, hence guarded.
- **(Session 18) A Material Return as an exact undo of FIFO draws:** refilling the last-drawn lot first leaves stock exactly as if only the consumed amount had been drawn by FIFO; the returned value is priced at those lots' own costs, so WO material cost must be issued − returned, not consumed × average cost (the average would leave a small rupiah gap between warehouse and WIP).
- **Effective-dated records** (labor rates, overhead rates): never UPDATE a rate — close the open one the day before the new one starts and insert a new row; "rate on date X" = started on/before X and not yet ended. Backdated rates are rejected because they'd overlap covered periods.
- **Snapshot vs. lookup**: a document copies the values it was approved with (WO: `hourly_rate`, `overhead_rate`, `work_center_id`, `work_order_materials`; PO: `unit_price`) so later master-data edits can't silently change it. A formula is a template used once at WO creation.
- **Derive, don't accept**: values derivable from other data (WO `product_id`/`work_center_id` from the formula, `created_by` from Auth) are never taken from the caller — nothing can contradict them.
- **A rule enforced at every step that depends on it** (`<<include>>` labor checked at create AND at release) — the step shouldn't trust that every path into it remembered.
- **Locking a parent row to serialize changes** when the thing to protect isn't one row (employee row while changing its open labor rate; work center row for overhead rates).
- **Deactivate instead of delete** for master data referenced by history (employees inactive, FKs `restrictOnDelete`).
- **Codes vs. document numbers**: dated documents carry a year (`WO-2026-…`, `RCV-2026-…`); master records don't (`EMP-000001`).
- **Reference data the schema depends on belongs in the migration** (work centers inserted by the migration that a later migration's required FK needs); sample data belongs in seeders.
- **Cost driver**: overhead follows the activity that causes it — machine hours, not labor hours (assembly: 32 labor h vs. 8 machine h).
- **Predetermined rate is an estimate even on actuals**: production results apply *actual hours × estimated rate*; only `overhead_expenses` are fully actual; the month-end variance reconciles them.
- **Warn at planning, enforce at execution** (material shortage chips on WO create; real stock check when materials are issued).
- **Prevent mistakes instead of reporting them** (already-chosen workers/products unpickable) — server validation and DB constraints stay as the safety net.
- **`<flux:error>` ignores its slot** — pass `:message="$message"` (or use `name="field"`). General lesson: when a vendor component silently does nothing, read its source.
- **Native `<select>` can't be styled per option** (browser/OS draws it) → custom listbox; you must re-add keyboard handling + ARIA (`listbox`/`option`/`aria-selected`) yourself.
- **A Blade component can't call the Livewire page's methods** (`$this` is the component) — pass prepared data in; `wire:click` inside still targets the enclosing Livewire component.
- **`<table>` shrinks columns to fit; a grid with fixed tracks + `minmax(0,1fr)` doesn't** — use grids for rows of inputs. **Container queries** (`@container` / `@3xl:`) adapt to the box's own width, not the viewport — right for components living in a narrow column.
- **Grid rows stretch cells by default** → a field with an error grows and drags its neighbour; `items-start` fixes it.
- **A CSS `transform` on an ancestor** (e.g. an animation with `fill-mode: both`) makes `position: fixed` children relative to that ancestor and creates a stacking context (later siblings can paint over popups) → use `backwards` fill so the transform is gone after the animation. **`overflow: auto/hidden` clips absolutely positioned popups.**
- **Don't `x-teleport` things Livewire re-renders**: Livewire re-syncs the teleported copy from server HTML and wipes Alpine's inline styles.
- **Don't rely on a DB default for a value code reads right after insert** — set it explicitly or `refresh()` (WO `status`).
- **`migrate:rollback` needs `--path` for subfolder migrations; `--step` counts migrations, not batches.** Edit a migration in place only while it's uncommitted (and roll back everything after it); once committed, add a new migration.
- **Livewire test harness**: authorization failures become a 403 response (`assertForbidden()`), not a thrown exception; render tests verify markup/behaviour, not visual layout.
- Predetermined (applied) overhead vs. actual overhead: actual bills/depreciation arrive monthly, but a production lot's `unit_cost` is stored at receipt time, so overhead must be applied immediately with a budgeted rate (BOP Dibebankan); the gap with actual is closed at period end as under/over-applied overhead (selisih BOP). Allocating actual overhead after the fact would mean rewriting costs of lots already consumed/sold downstream.
- Plan vs. actual are stored side by side, never overwritten (`work_order_labors` plan vs. `production_result_labors` actual; `quantity_target` vs. `quantity_good`) — variance analysis needs both numbers to survive.
- Composite (multi-column) unique constraints — the DB rejects duplicate *combinations*, regardless of which code path inserts them; each column alone can still repeat (e.g. the same material in different formulas). Used to make "one version number per product" and "one line per material per recipe" guarantees rather than conventions.

- MySQL auto-increment counters are not rolled back with a transaction — rolled-back inserts leave permanent gaps in id-derived document numbers.

You never call them yourself.
- `wire:model` vs `wire:model.live` is a **timing** difference, not a different sync mechanism: `.live` fires a request immediately on change/input; plain `wire:model` defers the value until *some* request happens for any reason (another `.live` field, a button click, etc.), at which point it rides along and syncs then. `updated()` fires for both — `.live` just controls *when*.
- `updated{PropertyName}()` (e.g. `updatedSupplierId()`) only works for plain top-level properties — Livewire generates that method name directly from the property name. Dotted array paths like `items.0.product_id` have no valid PHP method-name equivalent, so they only reach the generic `updated(string $name, mixed $value)` catch-all, matched via string/regex on `$name`.
- How a Blade `wire:model.live="items.{{ $index }}.product_id"` (inside a `@foreach`) links to the PHP `updated()` hook: there's no function call between them — Blade substitutes `{{ $index }}` at render time so each row's real HTML has a literal attribute like `wire:model.live="items.0.product_id"`; the browser reads that exact string off the changed element and sends it in the network request; Livewire uses it both to sync `$this->items[0]['product_id']` (via a dot-notation setter) *and* as the `$name` argument passed into `updated()`. One shared string does all three jobs.
- `updated()` is called **once per changed property, per request** — if a single request happens to carry multiple dirty properties (e.g. a deferred `wire:model` field riding along with a `.live` field's request), the hook runs multiple times in that cycle, once per property, each with its own `$name`/`$value`. This is why the regex guard inside it matters: the same hook sees every property change project-wide, not just the one you're targeting.
- `WithPagination`'s `resetPage()` is a thin wrapper over `setPage(1, $pageName)`, which sets `$this->paginators[$pageName] = 1` (an array, not a plain property — `$pageName` lets a component run multiple independent paginators). Calling it inside an `updating{Property}()` hook (e.g. `updatingSearch()`) guards against landing on a now-out-of-range page number after a filter shrinks the result set.
- `#[Url]` and `WithPagination`'s own `page` query-string registration are the *same underlying mechanism* (Livewire's query-string sync) applied two ways — one explicit via attribute, one automatic via the trait's `queryStringHandlesPagination()`. Both make component state bookmarkable/refresh-safe by syncing to the browser URL via `pushState`, not a full reload.
- **"Magic method" precision:** `updatingSearch()`, `updated()`, `mount()`, `rules()` etc. are *not* real PHP magic methods (`__get`/`__set`/etc., which the PHP engine itself recognizes). They're Livewire's own userland convention: `method_exists($this, $constructedName)` checks sprinkled through Livewire's own source, calling your method *in addition to*, not *instead of*, its normal internal behavior if found. Purely additive — never assume defining one "overrides" framework behavior.
- `dd()` is "dump and **die**" — it terminates the PHP process immediately after dumping. Fine for confirming a value in isolation, but leaving it inside a Livewire action method means the request never finishes rendering/responding — a symptom that looks exactly like "the UI isn't updating" is actually "the response never arrived because the script died mid-request." Remove it the moment the value is confirmed.
- A Laravel/Livewire project only needs **one** Alpine.js instance — Livewire bundles and auto-starts its own. Manually `import Alpine from 'alpinejs'; Alpine.start()` in `app.js` creates a second, independent instance racing the first to initialize on every page load, causing exactly the kind of order-dependent, hard-to-reproduce bugs (Flux's appearance/theme store silently losing its persisted value on some loads but not others) that don't throw errors because the two instances don't share Alpine's own duplicate-instance detection. To add an Alpine plugin safely, hook into Livewire's own instance via `document.addEventListener('alpine:init', () => Alpine.plugin(pluginFn))` instead of starting a second one.
- `@alpinejs/mask`'s `$money(input, delimiter, thousands, precision)` — verified from actual plugin source, not assumed: `delimiter` is the *decimal-point* character (defaults to `.`), not the thousands separator; `thousands` is the actual character inserted every 3 digits; get the argument order wrong and values silently land in the wrong slot rather than erroring. With `precision: 0`, feeding it a value that already contains a literal decimal point (e.g. straight from a `decimal:2`-cast Eloquent attribute, always `"30000.00"`) inflates the displayed number 100× — the mask strips the `.` as a non-digit and the trailing two decimal digits get absorbed as extra whole-number digits. Fix at the data source (cast to a whole-number string before binding), not by fighting the mask's config.
- Flux's `flux:input` component detects `.live` on the bound `wire:model` automatically and injects its own trailing loading spinner for free (`vendor/livewire/flux/stubs/.../input/index.blade.php`) — opt out per-field with `:loading="false"` if you're handling loading feedback yourself elsewhere (e.g. a scoped spinner in an adjacent cell via `wire:target`).
- **Why `purchase_order_receipts` exists as its own table, beyond "logging":** a single PO item can be fulfilled by multiple separate delivery events (e.g. 40 units Monday, 60 units Friday) — the receipts table is that event log, and `purchase_order_items.quantity_received` is *derived* from it (`SUM()` over receipts, recomputed, never incremented directly) — same "derived/cached field" pattern as `current_stock`/`total_amount`. This buys: (a) self-healing — the aggregate can't drift out of sync no matter how the underlying receipts change; (b) per-event accountability — each receipt has its own `received_by`/`received_at`, since different staff can receive different partial deliveries on different days; (c) it's the natural transaction boundary `ReceivePurchaseOrderAction` hangs one `CreateStockMovementAction` call on, one per receipt; (d) it's what makes FIFO lot-tracking possible later — a `stock_lot` is naturally one-per-receipt-event, not one-per-PO-item, since FIFO ordering is defined by *when each batch arrived*, not by PO creation time.
- **"Self-healing" describes the aggregate, not a license to edit receipt rows in place.** There's a real fork in how to "fix a wrong receipt": (1) edit the receipt row directly — simpler UI, but silently rewrites history (no record that 100 was originally claimed and later corrected to 85), which undermines the accountability point above; (2) never edit, record a correction as a *new* entry (reversal/adjustment receipt referencing the original) — preserves the full history, same posture `stock_movements` already takes elsewhere (`const UPDATED_AT = null`, immutable by design). `purchase_order_receipts` currently has a plain `updated_at` via `$table->timestamps()` (unlike `stock_movements`), so the schema itself doesn't force either answer — genuinely undecided, flagged against the receive-PO UI item below.
- **How a `Route::livewire(...)` page gets wrapped in a layout, traced end to end (Session 10):** a Livewire full-page component's own template renders to a plain HTML string first (`$content`). `Livewire\Features\SupportPageComponents\SupportPageComponents::renderContentsIntoLayout()` then generates and evaluates `@component($layout->view) @slot($layout->slotOrSection) {!! $content !!} @endslot @endcomponent` around it — `$layout->view` defaults to `config('livewire.component_layout')`, `$layout->slotOrSection` defaults to the literal string `'slot'` (Blade's convention for the *default* slot). So `$content` becomes the layout component's `$slot` variable with zero manual wiring in the page file itself. In this app: `components/layouts/app.blade.php` receives that as its `$slot`, wraps it in `<flux:main>`, and passes *that wrapped result* down as a new, separately-scoped `$slot` to `<x-layouts.app.sidebar>` — each component invocation gets its own local `$slot`, they are not the same variable just because they share a name. `sidebar.blade.php` then echoes its own `$slot` directly into `<body>`, next to the chrome it builds itself.
- **`Route::view(...)` pages vs. `Route::livewire(...)` pages — only the latter gets auto-wrapped.** `dashboard.blade.php` and `dashboards/placeholder.blade.php` are registered via plain `Route::view(...)` — no Livewire component involved at all, so `config('livewire.component_layout')` never applies to them; that's exactly why both explicitly self-wrap with `<x-layouts.app>` in their own template. Same story for the Fortify-resolved auth pages (login/register/etc.) — Fortify renders them as plain views too, so they also self-wrap (`<x-layouts.guest>`/`<x-layouts.auth>`). Only components registered via `Route::livewire(...)` (Create/List/View PO, the 3 Settings pages) rely on the config default, and a given component can still opt out per-instance via `#[Layout('some.other.view')]`.
- **`config('livewire.component_layout')`'s default (`'layouts::app'`) is a *namespaced view lookup*, not a component tag** — and it depends on a `Blade::anonymousComponentPath()` call existing somewhere, since that call is what registers the namespace. This is why Laravel's official Livewire starter kit ships that line as boilerplate; it's not app-specific config, Livewire's own package genuinely expects it. Removing it without also repointing `component_layout` breaks every `Route::livewire()` page silently (no error until an actual request/render is attempted) — see Session 10 above for the concrete break-and-fix.
- **Laravel service-provider registration order, and why `AppServiceProvider`'s `LoginResponseContract` override actually wins:** traced in `Illuminate\Foundation\Application::registerConfiguredProviders()` — providers register in this order: framework (`Illuminate\*`) providers first, then all Composer-auto-discovered **package** providers (this is where vendor's `Laravel\Fortify\FortifyServiceProvider` runs, which itself does `$this->app->singleton(LoginResponseContract::class, LoginResponse::class)` bound to *Fortify's own* default response), then finally the app's own `bootstrap/providers.php` list in file order (`AppServiceProvider`, then this project's `App\Providers\FortifyServiceProvider`). A container `singleton()` call doesn't stack — the second registration for the same abstract simply overwrites the first — so because the app's `AppServiceProvider::register()` runs *after* the vendor Fortify provider, its binding to the app's own `App\Http\Responses\LoginResponse` (role-based dashboard redirect) is the one still active when `AuthenticatedSessionController::store()` later calls `app(LoginResponse::class)`.
- **`'auth'` in `Route::middleware(['auth'])` is a Laravel built-in default middleware alias**, not something this project defines — resolves to `Illuminate\Auth\Middleware\Authenticate::class`, registered by the framework itself (`Illuminate\Foundation\Configuration\Middleware.php`). This project's `bootstrap/app.php` only *adds* `dashboard.access` to the same alias array; it never touches `auth`. Behavior: checks `Auth::guard(...)->check()`; if unauthenticated, throws `AuthenticationException` → Laravel's handler redirects to the `login` named route for a normal browser request, or returns 401 for a JSON request.
- **Parameterized route → Eloquent model binding for Livewire page components** works via `Livewire\Drawer\ImplicitRouteBinding`, which the class's own docblock says "mirrors the functionality of Laravel's `Illuminate\Routing\ImplicitRouteBinding`" (Livewire needs its own copy since a page component isn't a normal controller action, so the framework's own `SubstituteBindings` middleware doesn't cover it). **The match is by variable/property *name*, not by model class name** — proven from the actual matching code, `getPublicPropertyTypes($component)->intersectByKeys($route->parametersWithoutNulls())`: this intersects on array *keys* (names), the class name just rides along as the value for later. So `/purchasing/orders/{purchaseOrder}` binds to `public PurchaseOrder $purchaseOrder` because the *names* match (`purchaseOrder` ↔ `purchaseOrder`); the `PurchaseOrder` type hint only tells it *which class* to query once a name-match is found — swapping the route segment to `{order}` while keeping the property named `$purchaseOrder` would silently stop the binding, even though the type hint is unchanged. The actual DB lookup is Eloquent's own `resolveRouteBinding()` (effectively `PurchaseOrder::where('id', $value)->first()`, using the model's route key — `id` here, `PurchaseOrder` doesn't override `getRouteKeyName()`); a non-match throws `ModelNotFoundException`, which becomes a 404 *before* the component's `mount()` body ever runs — no manual `findOrFail()` needed. Resolution happens twice off one merged params array (once for `mount()`'s arguments, once for matching public properties), which is why `$this->purchaseOrder` is already the same resolved object by the time `mount()`'s first line executes.
- **`Model::load([...])` is Eloquent's "lazy eager loading"** (Laravel's own docblock: "Eager load relations on the model") — distinct from both **lazy loading** (touching an un-preloaded relation on the fly, e.g. `$po->supplier` with nothing pre-loaded — the N+1 risk when done inside a loop) and plain **eager loading** (`::with([...])` declared at the original query). `load()` is "lazy" only in *timing* — called after you already have the model instance (e.g. from route-model binding) — but "eager" in *behavior*: it batches one dedicated query per named relation (including one more per dot-nested level, e.g. `items.product`), not one query per access. This is why `$purchaseOrder->load(['supplier', 'createdBy', 'approvedBy', 'items.product'])` in View PO's `mount()` exists — it front-loads everything the template will touch in a fixed, small number of queries regardless of how many line items the PO has.
